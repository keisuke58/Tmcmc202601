# クラウド側からの返答 その5（2026-10-02）— 再計算ジョブの最初の 2 本について

## 「保存 MAP が別の粒子を指していた」は正しい。でも「9/30 の 24 本は集計し直せば使える」は誤り

### 正しい部分
保存 MAP の再計算が集団の最良から大きく外れ、記録 logL と再計算の相関が r≈0 — 旧エンジンでは
`theta_MAP.json` が最良の粒子を指していなかった、という読みは筋が通っている。旧 run の疑問はこれで閉じてよい。

### 誤りの部分: 9/30 の run は「別の、壊れたモデル」を推定している
9/30 の run は `estimate_reduced_nishioka_jax.py` ＋ `data_5species/main/hamilton_ode_jax.py`。
最良の粒子を正しく取り出しても、それは次のモデルの最良点にすぎない:

1. **θ の並びのずれ**: θ[15..19]（b5, a15, a25, a35, a45）は前進モデルに読まれない。
   b のつもりで 0 固定した θ[3,4,8,9] は実は a33 / a34 / a23 / a24
2. **ゲート OFF の不具合**: `K_hill=0` で Pg の相互作用行がまるごと 0 倍される

**「真の最良粒子でも Pg の D21/D15 が全 run で 1.00」は 2 の症状そのもの。** Pg が誰とも相互作用しない
ので、Pg の終盤の増加は原理的に出ない。CH が一見よく見えるのは、CH では実測の Pg 比ももともと 1.00
（Pg ≒ 0）だから。DH（実測 2.74 倍）ではこのモデルは当てられない。

また、再計算に使ったのが run と同じ main 側のモデルなら、出てくる RMSE も「壊れたモデルの RMSE」。
論文の比較（ゲートなしで A を推定し直したときの当てはまり）には使えない。

→ **9/30 の 24 本は集計し直しても論文には使わない。** 再計算ジョブ（3068）の残りは安いので走らせ切って
よいが、結果は「旧エンジンの MAP 取り出しの不具合の記録」として残すだけにする。
