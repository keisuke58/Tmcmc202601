## 結論: 待たずに本番 10 本を投入してほしい

理由は 2 つ。

### 1. 9/30 の run のエンジンは、新しいエンジンと別系統

| | 9/30 の run（f9f6e12 時点の `data_5species/main/tmcmc_nuts_engine.py`） | 新パイプライン（`tmcmc_engine_paper.py`） |
|---|---|---|
| 系統 | 2026-03-22 の `f7d9ca3` で書き換えられた 413 行の版 | **ba1c285（論文の本番）の版** |
| 両者の差分 | ── | **730 行**（`diff <(git show f9f6e12:…/tmcmc_nuts_engine.py) <(git show ba1c285:…/tmcmc_nuts_engine.py)`） |
| 粒子・箱の型 | **float32**（176〜186 行） | float64 |

「差分 145 行・ブックキーピング同一」は別のファイル同士の比較だと思う（colab_package 版か現在の main 版）。
9/30 の run を走らせたのは上の左の版。リサンプリングの 1 行が同じ形でも、周りの型と流れが違う。

新パイプラインで float32 が出てくるのは NUTS の受理判定の 2 か所（乱数との比較）だけで、粒子・logL の保存とは無関係。

### 2. 新パイプラインは「起きても必ず検出される」

- 新パイプラインでクラウド側が 3 本試した結果: 保存 logL と全粒子の再計算の max|差| = 0.0
- `8252ad5` 以降、**estimator が run ごとに全粒子を計算し直して照合**し、`run_record.json` に記録する
- `check_paper_runs.py` の判定 0 で、食い違った run は**自動で FAIL**（記録が無い run も FAIL）

なので、仮に新パイプラインで同じことが起きても、その run が黙って使われることはない。
**待つことで防げるリスクは無く、待つ分だけ GPU 時間が失われる。**

## 旧 run の食い違いの筋（Part A で 1 行で試せる）

9/30 のエンジンは粒子を **float32** で持っていた。`samples.npy` を読み込んで再計算するとき、
**float32 のまま JAX に渡した場合**と **float64 に変換して渡した場合**の両方で logL を計算し、
どちらが保存値と一致するかを見てほしい。`jax_enable_x64` は既定の型を変えるだけで、明示的に float32 の
配列を渡すとその型で計算が進む部分が残る。剛性の高い 2500 ステップの積分は、型の違いで大きくずれうる。
