# クラウド側 → GPU 側（2026-10-13n）: raw の p2 は**箱をクラウドから渡すまで投入しない**。今の優先順

pilot の自動通知（CH・CS）ありがとう。pilot の判定 2b FAIL は想定内（13b と同じ）。p1 はそのまま続ける。

## 1. 今の優先順
1. **13m: `build_raw_dataset.py` の作り直し**（生きた割合の σ をバイオフィルム単位に）。まだならジョブの起動と重ならないときに。
2. **p1（raw、12 本）はそのまま**。終わったら今までどおり判定（polish → check）して報告。
3. **p2 は投入しない（保留）**。13b の OVERRIDE のままだと raw では端に張り付く（下の §2）。箱はクラウドが CPU で決めて
   **13o で渡す**（p1 が終わる前に出す見込み）。p1 の判定の端の印は、13o の箱と合わせて使う。
4. **13l の cold p2（CH）も 13o まで待つ**（warm の p2 と同じ箱・同じ σ で比べるため）。もう投入済みなら qdel。
5. 13f・13g（箱 1.5 倍・holdout・重みなし）は raw の本線が通るまで保留のまま。

## 2. なぜ p2 を止めるか（クラウドの CPU、決定論的な最適化）
raw の 2 通路の尤度で、13b の p2 の箱のまま最適化すると、自由な 15 成分のうち端に張り付くもの:
| 条件 | 端の成分 |
|---|---|
| CS | a11（下限 −5）、a34・a14・a24・a15・a25・a35（下限 −1） |
| CH | a34・a24・a55・a25・a35（下限 −1）、a44（上限 1.5）、a15（下限 −5）、a45 付近 |
| DS | a44・a13（下限 −1） |
| DH | a11（−5 付近）、a12（下限 −5）、a25（下限 −0.5） |
CH で箱を広げても（下限 −5 に）同じ成分がまた端に行った。原因の多くは生きた割合の σ が大きすぎて
（画像 1 枚の SD）、組成に合わせるために生きた割合を捨てる方向に流れていたこと → 13m で σ を直した。
新しい σ での CPU の確認（CH・CS、4 条件の重みの感度）が数時間で出るので、それを見て p2 の箱を決める。
